# NETPIE Dashboard Field Mapping

Status: **built in NETPIE on 2026-11-20** (project `Smart-EV-Battery-Guard`, device `EV_Gateway`, dashboard `Charging Safety Monitor`). The widgets are generated by [`build_layout.py`](build_layout.py) into [`netpie_dashboard_layout.json`](netpie_dashboard_layout.json); the HTML widgets live in [`widgets/`](widgets/). Every field name comes from the Gateway aggregate telemetry table in [`../docs/data-contract.md`](../docs/data-contract.md). If the contract changes, update this file and the samples in [`../docs/samples/`](../docs/samples/) together.

NETPIE behaviour below was checked against the official manual at <https://docs.netpie.io/> and then **tested on the real platform** with the simulator. Items still marked **(verify)** were not testable yet.

## 1. How data reaches the dashboard

```
Gateway (MQTT) / simulator (REST) ──▶ NETPIE Device "EV_Gateway"
                               ├─ Shadow   (latest value of every field)  ──▶ Text, Gauge, Indicator, HTML widgets
                               └─ Feed     (time series, via Datatags)    ──▶ Chart widgets
```

- The Gateway publishes to MQTT topic `@shadow/data/update`; the simulator uses the equivalent REST call `PUT https://api.netpie.io/v2/device/shadow/data` (see `simulator/README.md` for why). Both require the contract object to be wrapped in `data`:

  ```json
  { "data": { "schema_version": 1, "temp_bat_c": 31.8, "state": "NORMAL", "...": "..." } }
  ```

- An optional top-level `"timestamp"` (Unix epoch in **ms**) sets the time of the data point. Without it NETPIE uses the time the server received the message. A timestamp older than the Shadow's latest value goes into the Feed only and does not update the Shadow. That makes it usable for replaying data sent late after a Wi-Fi outage.
- `timestamp_ms` in the contract is **Gateway uptime**, not wall-clock time. Do not send it as NETPIE's top-level `timestamp`.
- Each dashboard widget reads one Device through these references:

  | Reference | Returns |
  | --- | --- |
  | `#["EV_Gateway"]["shadow"]["<field>"]` | Latest Shadow value; nested objects use more keys, for example `["validity"]["temp_bat"]` |
  | `#["EV_Gateway"]["status"]` | `1` = device connected to NETPIE, `0` = not connected. **Tested:** the dashboard only reflects an MQTT connection. REST writes (with LivenessTTL on) make the REST `/status` API report `1`, but the dashboard indicator stayed `0`. |
  | `#["EV_Gateway"]["feed"]` | Time-series data for Chart widgets |

  In the editor, type `#` or click **+ Device** to autocomplete. The Device must first be added under the dashboard's **Setting → Add device**, with **Read Shadow** and **Read Feed** privileges. Do not grant Write Shadow or Publish Message, because there are no remote controls yet (see §6).

## 2. NETPIE device setup

| Item | Value / decision |
| --- | --- |
| Device name / alias | `EV_Gateway` (use exactly this name in every widget reference) |
| Credentials | Client ID, Token, Secret go into the **ignored** local config only. Never put them in this folder or in an exported layout. |
| Schema `additionalProperties` | `true` for now, so a newly added field is not silently dropped |
| Schema `minimum` / `maximum` | **Do not set** for now. NETPIE silently drops values that fail validation, which would hide real out-of-range readings. |
| Field names | Contract names already meet NETPIE's rule (`a-z A-Z 0-9 _` only) |

### Feed datatags (history for charts)

Create one Datatag per numeric field under **Device → Feed → + Add datatag**:

| Data Path | Data Type | Unit | Used by chart |
| --- | --- | --- | --- |
| `temp_bat_c` | Number | °C | Battery temperature |
| `temp_rate_c_per_s` | Number | °C/s | Battery temperature (2nd Y axis) |
| `current_a` | Number | A | Charging current |
| `gas_raw` | Number | raw ADC | Gas raw reading |
| `temp_ambient_c` | Number | °C | Ambient |
| `humidity_pct` | Number | % | Ambient |
| `power_cut` | Number | 1=cut | Events (step chart) |
| `flame_detected` | Number | 1=flame | Events (step chart) |

- **Tested:** NETPIE fixes the Data Type to Number and stores `false`/`true` as `0`/`1`.
- **Tested:** a `null` field is removed from the Shadow (see §4), so it adds no Feed point and leaves a gap rather than a false 0.
- All 8 datatags use **TTL 1 week**.
- **Free quota (from docs.netpie.io/quota-netpie.html):** 500,000 Shadow writes/month, 1,000,000 Feed point-months, 800,000 API calls/month. One message per second around the clock would be about 2.6 million writes a month, so the continuous publish rate must be about one message every 6 s or slower. A 1 s rate is fine only for demo sessions of a few hours. This is open decision 4 in §7.

## 3. Field-to-widget mapping

"Source" shows which board produces the value. Node-sourced values go stale when the ESP-NOW link stops (see §4).

| Field | Source | Widget(s) | Title / unit | Display range | Notes |
| --- | --- | --- | --- | --- | --- |
| `state` | Gateway logic | **HTML** state banner (§5) | System state | n/a | Indicator Light only supports 2 states, so use HTML for multi-state colour |
| `power_cut` | Gateway | Banner chip | Charging power | CUT / supplied / unknown | Shown as a chip inside the state banner |
| `temp_bat_c` | Node (DS18B20) | Text (Big) + Gauge + Chart | Battery surface temp, °C | 0–100 | 1 decimal |
| `temp_rate_c_per_s` | Gateway logic | Text + Chart (2nd axis) | Temp rise rate, °C/s | can be negative | 2 decimals; optional field, so hide the panel if not implemented |
| `gas_raw` | Node (MQ-135) | Text + Chart | **Gas (raw ADC, uncalibrated)** | 0–4095 (verify ADC resolution) | Never label as ppm |
| `flame_detected` | Node (KY-026) | Indicator Light, blinking | Flame | ON = detected | ON colour red, BLINKING bound to the same value |
| `current_a` | Gateway (ACS712 5 A) | Text (Big) + Gauge + Chart | Charging current, A | 0–5 | Direction/sign still undecided; widen to −5…5 if negative values appear |
| `temp_ambient_c` | Gateway (DHT11) | Text + Chart | Ambient temp, °C | 0–50 | DHT11 rated range |
| `humidity_pct` | Gateway (DHT11) | Text + Chart | Humidity, % | 0–100 | |
| `node_age_ms` | Gateway | Text + banner | Node data age, s | n/a | Show as seconds; drives the stale rule |
| `node_sequence` | Gateway | Text (diagnostics) | Node message # | n/a | Should keep increasing; a frozen value means no new Node data |
| `button_event` | Gateway (KY-004) | Text (diagnostics) | Last button event | n/a | Shows `STOP` / `RESET` / `—` |
| `validity` | Gateway | HTML (diagnostics table) | Sensor health | n/a | Object shape is still a draft; see §7 |
| `timestamp_ms` | Gateway | Banner chip + Text (diagnostics) | Gateway uptime | n/a | Banner shows `Xm Ys`; not wall-clock time |
| `schema_version` | Gateway | Text (diagnostics) | Contract version | n/a | Must match the version this mapping was written for (1) |
| (device) `status` | NETPIE | Banner (title + chip) | Gateway online | 1 / 0 | Source of the dashboard-only `OFFLINE` display |

**Gauge colour bands.** Leave gauges single-coloured until the team agrees on thresholds. Coloured bands look like safety limits, and the repo does not yet have any validated limits. When thresholds are agreed, take the band edges from the same place the firmware reads them, not from this file.

**Text widget values.** Use a JS expression with a fallback so that a missing value never shows as `0` or `undefined`. **Tested:** the VALUE box accepts JS. This is the form `build_layout.py` generates:

```js
(function (v) { return (v === null || v === undefined || v === "") ? "—" : (Number(v)).toFixed(1); })(#["EV_Gateway"]["shadow"]["temp_bat_c"])
```

A Gauge cannot show "no data", so always pair it with a Text widget or the banner showing the unavailable state.

## 4. Display rules: unavailable, stale, offline

Apply these rules in this priority order:

| Priority | Condition | What the dashboard shows |
| --- | --- | --- |
| 1 | `#["EV_Gateway"]["status"] == 0` | Banner turns grey and reads **OFFLINE: Gateway not connected**. All values stay visible but are labelled "last known". |
| 2 | `node_age_ms > STALE_MS`, or `validity.node_link == false` | Node-sourced fields (`temp_bat_c`, `gas_raw`, `flame_detected`) are greyed and labelled **stale**. |
| 3 | Field is `null` / missing, or its `validity` flag is `false` | Show `—` with the label **no data / sensor error**, never `0`. |
| 4 | Otherwise | Normal display |

- `STALE_MS` is not in the contract yet. Define it once (for example as a constant at the top of the banner HTML) and align it with the Gateway's own Node timeout when that is decided.
- **Null in Shadow (tested).** Writing `null` removes the field from the Shadow, so widgets read it as `undefined`. The fallback expressions and HTML widgets handle both `null` and `undefined`. Firmware must therefore not rely on a `null` staying visible: the `validity` flags are what tells the dashboard a reading is bad.
- **Offline while testing with REST.** Because the dashboard's `status` follows the MQTT connection only, the banner shows `OFFLINE (last known: …)` while the simulator publishes over REST. The other widgets still update. With the real Gateway on MQTT this should show online; confirm once the firmware connects.

### State colours

The contract does not fix state names yet. The banner should support the names proposed in `software_checklist.md` and show anything else as "unknown":

| State | Colour | Banner text |
| --- | --- | --- |
| `STARTING` | Blue `#1565C0` | Starting up / sensors warming |
| `NORMAL` | Green `#2E7D32` | Normal |
| `WARNING` | Amber `#F9A825` | Warning: check the battery |
| `HAZARD` | Red `#C62828` | HAZARD: charging power cut |
| `SENSOR_ERROR` | Purple `#6A1B9A` | Sensor error |
| `OFFLINE` | Grey `#616161` | Gateway offline (dashboard-derived) |
| anything else | Grey `#616161` | Unknown state: `<value>` |

`OFFLINE` cannot be sent by the Gateway, because an offline Gateway cannot publish anything. The dashboard derives it from `#["EV_Gateway"]["status"]`.

Show the HAZARD banner text as "charging power cut" only when `power_cut` is actually `true`. Otherwise show "HAZARD: power cut **not confirmed**". The dashboard must report what the Gateway says happened, not what is expected to happen.

### State banner (HTML widget)

The live code is [`widgets/state_banner.html`](widgets/state_banner.html); the diagnostics table is [`widgets/sensor_health.html`](widgets/sensor_health.html). What testing showed:

- NETPIE substitutes each dollar-brace `#[...]` reference with the raw value before the script runs, so string values must be inside quotes.
- The widget re-renders whenever a referenced value changes.
- **Pitfall:** NETPIE evaluates that reference syntax **anywhere** in the HTML, including inside HTML comments. A placeholder like `#[...]` written in a comment broke the whole script (`SyntaxError: Unexpected end of input`). Never write it in comments.

The early draft below is kept for reference; use the files in `widgets/`.

```html
<div id="banner" style="padding:16px;border-radius:6px;color:#fff;font:600 22px sans-serif;text-align:center"></div>
<div id="sub" style="margin-top:6px;font:14px sans-serif;text-align:center;color:#555"></div>
<script>
  const STALE_MS = 5000; // placeholder until the contract defines the Node timeout
  const online   = Number("${#["EV_Gateway"]["status"]}") === 1;
  const state    = "${#["EV_Gateway"]["shadow"]["state"]}";
  const powerCut = "${#["EV_Gateway"]["shadow"]["power_cut"]}" === "true";
  const ageRaw   = "${#["EV_Gateway"]["shadow"]["node_age_ms"]}";
  const ageMs    = (ageRaw === "" || ageRaw === "null" || ageRaw === "undefined") ? null : Number(ageRaw);

  const STATES = {
    STARTING:     ["#1565C0", "Starting up"],
    NORMAL:       ["#2E7D32", "Normal"],
    WARNING:      ["#F9A825", "Warning: check the battery"],
    HAZARD:       ["#C62828", powerCut ? "HAZARD: charging power cut" : "HAZARD: power cut NOT confirmed"],
    SENSOR_ERROR: ["#6A1B9A", "Sensor error"]
  };

  let [colour, text] = STATES[state] || ["#616161", "Unknown state: " + state];
  if (!online) { colour = "#616161"; text = "OFFLINE: Gateway not connected (last known: " + state + ")"; }

  let sub = "Charging power: " + (powerCut ? "CUT" : "supplied");
  if (ageMs === null)         sub += " · Node data: none";
  else if (ageMs > STALE_MS)  sub += " · Node data STALE (" + (ageMs / 1000).toFixed(1) + " s old)";
  else                        sub += " · Node data " + (ageMs / 1000).toFixed(1) + " s old";

  const b = document.getElementById("banner");
  b.style.background = colour;
  b.textContent = text;
  document.getElementById("sub").textContent = sub;
</script>
```

### Pane widths on NETPIE (freeboard)

- Freeboard computes a fixed column width from the window width when the page loads: about 219 px minimum per column, so roughly 4 columns at 1280 px and 5 at 1440 px. A pane cannot stretch; its width is `col_width` columns, clamped to the visible column count.
- `build_layout.py` therefore gives the status and diagnostics panes `col_width` 16, which always fills the screen. The four metric panes are 2 columns wide and packed as many per row as fit. That fills the width on even column counts (for example 1280 px) and leaves one empty column on odd counts (for example 1440 px). A stretchy two-up grid like the mockup is not possible in freeboard.
- Rows only set the order. Gridster pushes overlapping panes down, so small row numbers pack the page without gaps. It may swap Charging and Ambient to fill space.

### Theme pitfall: white text

NETPIE's freeboard theme sets widget text to white while panes are white. Text-widget units and any HTML-widget text without an explicit colour are invisible. The state banner widget injects `.tw-unit { color: #5F6670 }` for the whole dashboard, and the HTML widgets set their own text colours.

## 6. Remote controls

**None for now.** This follows `dashboard/README.md` and `docs/architecture.md`. Do not add Button, Toggle or Slider widgets, and do not grant the dashboard **Write Shadow** / **Publish Message** privileges, until the team has defined:

- the command path (Shadow write or `@msg` topic) and how the Gateway acknowledges it,
- how the dashboard shows command status (sent / accepted / rejected),
- a rule that a cloud command can never silently re-enable charging.

## 9. Backups and rebuilding

- The source of truth is [`build_layout.py`](build_layout.py). Edit it (or the files in `widgets/`) and run `python dashboard/build_layout.py` to regenerate `netpie_dashboard_layout.json`. That file holds only `panes`: no datasource token and no Device keys.
- To apply it, open the dashboard and click **Edit**. In the dashboard iframe's browser console run `cfg = freeboard.serialize(); cfg.panes = <panes from the JSON>; freeboard.loadDashboard(cfg)`, then click **Save**.
- NETPIE's own **⋮ → Export** includes a short-lived dashboard token (`dashtoken`). Do not commit an export without removing the `datasources` section first.
